## Configuration and security controls observed

Hosted production rejects DEBUG=true, development mode, weak/missing SECRET_KEY, wildcard hosts and insecure CSRF origins. Railway defaults enable HTTPS redirection, secure session/CSRF cookies, HttpOnly session cookies and HSTS. Forwarded TLS/IP headers still require the actual trusted ingress to sanitize them; source configuration cannot establish that property. Preserve the deployed signing secret during release to avoid unintended session invalidation.

Media/API viewer-dependent responses are private/no-store. Private media routes resolve the database owner and enforce profile, portfolio, conversation, lesson or verification-review permissions. New private Cloudinary uploads use authenticated delivery. CDN cache rules must honor app response headers and must not cache authenticated/private routes or publish MEDIA_ROOT through a static origin. No arbitrary user media URLs were fetched during this audit. Current Wrangler source has no static asset binding, but old generated inspection files do not prove today's Cloudflare routing or cache rules.

Redis fail-closed controls are present and isolated cross-process tests verify atomic counters/leases locally. TURN uses derived expiring credentials and no-store responses; shared-secret validation and per-account token buckets remain in place. Default credential TTL is one hour; selected transport and renewal still require live verification.

The workspace contains many pre-existing modified and untracked application/security modules and migrations. A deployment built from Git HEAD may omit them. Packaging is also ambiguous locally: tracked requirements.txt pins Django 6.0.9/DRF 3.17.2, while ignored pyproject.toml and requirements.render.txt still specify older versions. Verify the actual build input; neither an ignored local lockfile nor a successful local environment proves the Railway image contents.

## Migration assessment

Subsequent local fixes are documented in [migration safety fixes](migration-safety-fixes-2026-10-28.md): pending historical messaging upgrades preserve authoritative participants, a forward migration retains and retires legacy call decisions, whole-plan preflight rejects known unsafe reversals before earlier migrations reverse, and exact-definition index recovery handles interrupted concurrent DDL. Already-lost conversation mappings still require reviewed backup evidence; production target inspection and a verified recoverable production backup remain gates. These are local changes, not a deployment or a production repair.

Follow-up: the [populated PostgreSQL rehearsal](populated-postgresql-migration-rehearsal-2026-10-28.md) exercised the current 15-migration batch and a synthetic dump/restore successfully. It also reproduced historical messaging data/access hazards, partial reversal before a consent guard, and a non-atomic concurrent-index retry failure. Target production history/schema inspection, a verified recoverable production backup, and reviewed recovery procedures remain release gates. No production migrations were run.

The dry-run makemigrations check reported no changes; the migration graph reported no conflicts. The isolated SQLite test database built successfully. New pagination/index migrations use non-atomic PostgreSQL concurrent index operations via config/migration_operations.py. SQLite tests do not execute that PostgreSQL path or validate target lock duration, invalid concurrent indexes, exclusion constraints or existing-data backfills. Applied-history and physical-schema inspection remain required. Production migrations were not run.

## Verification and boundaries

The [offline historical Cloudinary exposure audit](cloudinary-exposure-audit-2026-10-28.md) prepares identity-preserving migration, CDN revocation and verification procedures without production access or file deletion. Historical asset inventory, custom/signed URL coverage, namespace policy exceptions and actual edge revocation remain unresolved until separately authorized verification; application ACL tests do not clear that gate.

The later [offline backup/restore readiness audit and recovery checklist](backup-restore-readiness-audit-2026-10-28.md) reviews the existing evidence without accessing production. It corrects the older isolated-restore guidance, distinguishes synthetic drill success from actual production recoverability, and leaves current backup coverage, owner-approved RPO/RTO and real-backup restore verification blocked pending authorized operator evidence.

The reusable runner is `scripts/audit_production_readiness_local.py`. It disables dotenv, strips application/service environment secrets, retains only Windows runtime paths, blocks outbound network calls while allowing asyncio socketpair wakeups, and uses in-memory SQLite/cache/Channels, temporary media and nondelivery email. Fixture password hashing is accelerated only inside that process. It performs graph/model checks before selected regressions.

Completed independent checks:

- 74 selected Node regressions passed: call/classroom ICE policy, socket authentication, private media URL handling, upload safety, release configuration and dependency compatibility.
- Four real Redis fixture tests passed, including independent-process quota/lease races and admin authentication protection. The runner created its own memory-only password-protected loopback instance and shut down that verified fixture; it did not use production REDIS_URL.
- Python pip check reported no broken requirements. This checks compatibility, not vulnerability absence; a complete fresh Python CVE audit was not performed.
- Fresh npm advisory query completed after a sandbox-limited attempt failed. Raw ignored local evidence: `.audit-production-readiness/npm-retry.json`. No package mutations occurred.
- Both read-only Railway backup attempts returned INCONCLUSIVE. No successful live metadata, production DB, deployed Redis, live TURN, actual CDN-denial test, mobile native build or browser-device media test can be claimed.

Historical backend audit result: **357 run, 354 passed, one failed, two skipped**, recorded in `.audit-production-readiness-local-final.log`. The initial harness also encountered an OpenSSL entropy setup error after stripping Windows OS paths; retaining the OS runtime paths cleared that setup error. The ASGI fixture failure was subsequently fixed by deferring the migration dry-run; `.audit-asgi-upload-broader-final.log` records **363 run, 361 passed, two skipped, no failures or errors**, and `.audit-asgi-upload-focused-final.log` records 49 passing focused checks. The two skipped shared-admin Redis tests require their explicit runner; the separate real Redis run exercised one shared-admin integration check and all three resource Redis checks, not every skipped admin race scenario. No application runtime code was changed to obtain these results.
