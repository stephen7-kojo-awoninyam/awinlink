## 3. Candidate freeze and offline/staging checklist

- [ ] Name release commander, database operator, security/privacy approver, mobile/QA owner, monitoring owner and alternates; record scope and maintenance window in UTC.
- [ ] Freeze the concrete release revision and image/asset/dependency digests, including current untracked security files and migrations. Review diffs; do not indiscriminately commit audit databases, journals, secrets or private URL lists.
- [ ] Resolve packaging ambiguity, rebuild in a clean environment and run relevant candidate checks. Preserve pinned Expo/WebRTC compatibility and the scoped dependency regressions. Refresh vulnerability evidence through an authorized registry route; triage remaining findings and scope any accepted risk explicitly.
- [ ] Preserve current security invariants: role escalation denial, active/revoked account checks, CSRF/JWT/session/socket revocation, authorization before media reads, no-store/private caching, signature/MIME/size checks, account/global resource budgets, idempotency and consent evidence. Existing administrators, calls and legitimate readers must retain intended behavior.
- [ ] Complete isolated PostgreSQL/Redis integration and restored-copy upgrade/rollback rehearsal. Do not run application tests against production. Verify schema/model drift and target privileges/extensions, index recovery, sequences, duplicates/consent and critical data fingerprints.
- [ ] Use separate test media/cloud/account/Redis targets and nondelivery/mock external services until a specific controlled live verification is authorized. Disable erasure, notification and other automatic side effects in restored environments.
- [ ] Test existing and candidate web/native clients against the candidate backend: pagination/Link continuation, signed cursors, upload streaming, signaling aliases, first-handshake auth renewal, old/new session behavior and private media. Do not assume all installed clients update together.
- [ ] Attach B1–B10 evidence or explicit approved scope decisions before scheduling the production change. A checklist tick is not a substitute for the evidence reference.

| 5. Backend/web canary | Start the candidate ASGI backend and matching static/web assets with existing signing identity and compatible client contracts. | 6. Historical media remediation | Only after the candidate ACL/proxy and authenticated playback work, execute a separately approved single-asset Cloudinary canary, then bounded manifest batches, followed by explicit CDN verification. Keep the affected surface isolated until confidentiality gates pass. | B6 evidence; preserve bytes/public IDs/journal and required derivatives; never change back to public delivery on failure. Backend deployment alone does not clear this gate. |
| 7. Reopen in controlled steps | Reopen only approved features, then compatible jobs individually. Test call/relay policy, auth recovery and current permissions with controlled accounts. Keep destructive erasure execution and new payment collection disabled unless separately authorized and validated. Verify replacement backup/alerts before normal traffic. | Data/security metrics and designated smoke tests pass; no unresolved in-scope gate. Record first new writes for any recovery decision. |
| 8. Distribute native clients last | After backend contracts are stable, validate signed native artifacts on devices and obtain separate distribution approval. Preserve compatibility with already installed clients and observed server handshake behavior. | B9/B10 and enabled feature gates; no automatic store submission, EAS Update, new signing key or payment activation. |

The sequence does not assume additive schema compatibility. Added columns, irreversible data normalization, resource/pagination contracts and mixed-version workers must be checked against the actual old and new releases. If compatibility is unknown, stop writes/traffic for the affected scope rather than improvise a rolling update. Do not claim preservation of active calls across a drained worker restart without measured support.

## 5. Rollback and stop gates

| Trigger/state | Allowed prepared response | Must not do |
| --- | --- | --- |
| Before any mutation | Stop; retain the existing verified release and evidence. Resolve the blocker first. | Deploy an unreviewed image or remove security checks to pass startup. |
| Canary app regression; schema still compatible | Stop rollout; use the reviewed known-good artifact only after verifying schema, signing/session, client-contract and security compatibility. Prefer a forward correction if the old artifact reintroduces an audited vulnerability. | Treat “previous version” as automatically safe or weaken auth/ACL/resource limits. |
| Interrupted index migration | Stop the migrator; compare recorder and exact index catalog state. The current helper can reuse exact valid indexes, rebuild exact invalid leftovers and tolerate already-dropped reverse indexes. Resume only the reviewed plan with one runner. | Blindly fake history, drop a mismatching index, bypass a guard or manually mark the migration complete. |
| Irreversible or populated-table reverse plan; retained coach/scout links | Whole-plan preflight must stop before any earlier migration reverses. Standard migrate uses the hook; programmatic tooling must use SafeMigrationExecutor. Choose reviewed forward correction or approved replacement restore. | Bypass the guard with raw MigrationExecutor/--fake, remove consent/history links or assume multi-migration rollback is atomic. Runtime failures can still partially apply an admitted plan. |
| Data corruption or incompatible schema after new writes | Contain writes/jobs, preserve original state and restore into a separately validated replacement. Quantify/reconcile post-backup writes, payment side effects, deletions/holds, memberships and token/password revocations. Obtain explicit recovery/cutover approval. | Overwrite the live database, restore a production snapshot as a rehearsal, lose new writes silently or switch between two writable divergent databases. |
| Historical media move or playback failure | Pause batches, preserve journal and immutable identities, keep authenticated origin private; investigate delivery/derivatives and provider invalidation coverage. | Delete assets, overwrite collisions, republish upload/private delivery, regenerate an in-progress manifest or equate origin success with CDN revocation. |
| Redis/auth/resource failure or ingress spoofing | Stop affected traffic/rollout; repair the required shared service or trusted ingress and verify controlled recovery. | Fall back to process-local security counters, trust arbitrary forwarded headers, ignore 503s or disable fail-closed protection. |
| Relay-only TURN failure | Pause affected call entry/release and repair relay connectivity/configuration; keep the approved privacy policy. Preserve supported existing call/session behavior where safe. | Automatically switch relay to all when peer-IP privacy was promised; rotate the shared secret without refresh/overlap planning. |
| Secret/HSTS/client/native incompatibility | Escalate to the owner; preserve signing identity unless an explicit rotation incident plan is approved. Verify new/old clients and native module compatibility before a server rollback. | Assume code rollback recalls browser HSTS, restores revoked CDN copies, reverses third-party sends/charges, or changes installed native binaries. |
| Erasure/notification/payment side effects | Pause the affected job path, preserve receipts and authoritative provider evidence; reconcile before replay or restore. | Blindly repeat sends/refunds/deletions or use a migration manifest as a deletion list. |

Global stop criteria: any private-data disclosure, unauthorized role/membership action, consent/history loss, corrupted financial evidence, invalid/unexpected schema, failed backup verification or required protection failing open. Availability signals alone never override these criteria. Incident/rollback decisions need named owners, timestamps and evidence; thresholds for error rate, latency, Redis/DB load and call quality must be agreed before rollout, not invented mid-incident.
